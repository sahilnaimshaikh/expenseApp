# Performance Test Instructions — Expense Tracker

## Purpose
Validate the app meets requirements.md's NFR-1 (2s launch, "lightning fast" expense entry, 60 FPS animations) and NFR-2 (500,000+ expense records handled efficiently) under realistic data volumes.

## Performance Requirements (from requirements.md / PRD)
- **App launch**: ≤ 2 seconds cold start
- **Add Expense save**: feels instantaneous (no fixed number — "lightning fast"); target ≤ 300ms perceived latency for the save action itself
- **Dataset scale**: smooth operation (list scroll, search, filter, reports) with 500,000+ Expense records
- **Animations**: sustained 60 FPS during scrolling and chart transitions

## Run Performance Tests

### 1. Cold Start Time
```bash
flutter run --profile
# Use Flutter DevTools' Timeline view, or:
adb shell am start -W -n <package>/<activity> 
# to measure "TotalTime" for cold start
```
**Expected**: ≤ 2000ms to first frame of the Dashboard (or Onboarding, on first launch).

### 2. Expense List Scroll Performance at Scale
With 500,000+ rows seeded:
1. Open the Expense List screen.
2. Scroll continuously for 10+ seconds.
3. Use Flutter DevTools' Performance view to check for dropped frames.

**Expected**: Sustained ~60 FPS; no more than occasional single-frame drops during scroll. `ExpenseListController` implements incremental pagination (50 rows/page via `load()`/`loadMore()`, triggered by a `ScrollController` listener in `expense_list_screen.dart` — added during Build and Test prep after this gap was identified) rather than a single large fetch, per nfr-design-patterns.md's "Paginated list pattern." Verify on-device that the 300px scroll threshold feels responsive (adjust in `_ExpenseListScreenState.initState` if pages load too late/early in practice).

### 3. Search/Filter Latency at Scale
1. With 500,000+ rows seeded, use the Expense List's search bar.
2. Measure time from keystroke to updated result list.

**Expected**: Sub-second response. **Known risk**: `ExpenseService.searchExpenses()` currently fetches the entire matching date-range (or all rows, if unfiltered) into memory before filtering in Dart (see business-logic-model.md Process 1) — at 500,000+ rows this could exceed the "instant search" goal. If this test fails, the fix is to add a date-range default to `searchExpenses` (e.g., default to the last 12 months) rather than truly unbounded search.

### 4. Report Aggregation Latency
1. With 500,000+ rows across 12+ months, open each Reports tab.
2. Measure load time.

**Expected**: Sub-second per report — `ReportService`'s methods already query by date range first (indexed) before aggregating, per the narrow-then-aggregate pattern, so this should scale well. Verify this holds in practice.

### 5. Chart Animation Frame Rate
Open Dashboard and Reports screens; observe the `PieChart`/`LineChart` animations added in Unit 7.

**Expected**: Smooth 300ms transitions with no visible stutter.

## Performance Optimization

If any test above fails:
1. **Expense List scroll jank**: implement the missing infinite-scroll trigger in `expense_list_screen.dart` (listen to the `ListView`'s `ScrollController`, call `ExpenseListController`'s pagination with incrementing `offset`).
2. **Search latency at scale**: bound `searchExpenses`'s default query to a recent date range, or (longer-term) consider an Isar full-text index if search remains a bottleneck after bounding.
3. **Report latency**: profile with DevTools to confirm the date-range filter is actually reaching Isar's index (not being applied after a full fetch) — re-verify the `.optional()` chain in `ExpenseRepository.query()` compiles to an indexed query, not a full scan, once the SDK/build_runner output is available to inspect.
